# P2C2-vault: fence collision and directional injury

Status: implemented in **0.2.4** under the owner's 2026-09-27 fence-style collision selection (C34). Automated/native validation passes; rendered SP acceptance is pending. The combined owner test below includes the unaccepted 0.2.3 repair. No earlier checkpoint is retrospectively accepted.

## Behavior

New native Building construction and finished-item deployment create two aligned fence edges with one shared durability pool. The build footprint remains 1x2, two across and one deep. Players can occupy the ground behind the blocking edge; ordinary walking across it stays blocked. Zombies cannot use the ordinary low-fence hopping route and must thump or route around it.

Stand immediately in front of or behind either half, right-click the barrier, then select **Spike Barrier > Vault**. The label identifies a safe rear or front scratch risk. This checkpoint deliberately uses an explicit action; the normal fence key is not integrated. The action inherits the installed ISClimbOverFence facing/queue behavior and calls the public native climbOverFence entry. It does not teleport the player, change shared pass-through flags, or rewrite native state parameters.

The front performs one `ZombRand(5)` hazard roll after the native animation leaves the fence state successfully onto its expected landing and returns to idle/movement. A zero applies one lower-leg environmental scratch, with a separate random left/right selection. The rear performs no hazard roll. A failed/blocked/interrupted/dead-player/removed-barrier attempt does not roll. God Mode suppresses injury. This is a flat 20 percent risk without a clothing-protection reroll; native wound severity and healing traits apply. The scratch does not roll Knox infection; ordinary wound care still applies.

Loaded floor, same level, immediate front/rear approach, exact paired identity, native landing/wall checks and a clear landing are required. Occupants, vehicles, water, stairs and full-square thumpables reject the action. The native engine retains its additional climb restrictions. A bounded tracker watches only active local-player crossings, logging start, native entry and one terminal result. Rejected native entry expires without moving or damaging the player.

Older built barriers keep full-square collision and can be picked up/redeployed once to convert. They show that instruction in the submenu. Debug-place prototypes remain legacy fixtures; use native Building for the new checkpoint. New edge barriers cannot use the old debug post-placement rotation: pick up and rotate the native placement preview when redeploying. Free ten-second repair/pickup, full-condition recovery, five-item bundles, approved recipe/XP and 0.2.3 Sandbox damage/HP settings are unchanged.

## Engine implementation and evidence

- The construction wrapper changes only the registered OMHTT part sprites' native north/west orientation before the IsoThumpable constructor. This fixes south-facing cursors supplying `north=false`. Record and object markers persist `collisionModel = edge-v1`; old records with no model remain full-square.
- Native collision uses `blockAllTheSquare=false`, `canPassThrough=false`, `isHoppable=false`. The installed C++ pathfinder additionally requires wall metadata. At tile initialization, direct WallN/W and TallHoppableN/W properties expose the edge to both pathfinders while keeping the ordinary zombie hopping flag false. CantClimb prevents an untracked generic wall-climb route. Direct property registration avoids the tile loader's automatic wall type/collision transformations; the existing white marker images and registered tile identities are unchanged. The explicit action selects the low-fence animation despite the pathfinding metadata.
- Retaliation classifies the front/rear against the actual zero-depth blocking edge, retaining front/side damage and a safe rear. The existing two-tile health and retirement code remains authoritative.
- `tools/validate_foundation.py`: 535 Kahlua assertions, 19 modules, 92 native JSON translation keys, 23 native packet serializations and a 71-file package manifest. Tests cover all four headings, both halves/both approaches, native wrapper orientation, blocked/occupied/native-rejected landings, one roll, rear safety, God Mode, failed outcomes, hit interrupts after movement, timeout, death, removal and prior servicing/bundle/settings cases. World/UI actors in these tests are controlled doubles.
- `tools/NativeVaultProbe.java`, invoked during the native smoke: actual installed IsoThumpable, IsoGridSquare and IsoPlayer objects. Both directions block walking/path collision; both Java and C++ pathfinder classifiers recognize thumpable edges. Public climbOverFence reports EventClimbFence in E/W/S/N, then native state execution crosses the expected edge with an actor-scoped collision exception bounded to its rectangle/floor. Fixtures supply animation variables explicitly and do not represent a rendered loaded-area playtest.
- Native Lua bridge verifies the environmental lower-leg scratch with no Knox infection. Native serialization writes and reads eight legacy full-square parts plus eight directional edge parts at 37/200 HP, preserving exact native sprite/config identity, orientation, owner and collision marker. A separate server process reloads those bytes.
- Evidence: `diagnostics/v0.2.4/validation.log`, `manifest.json`, `server-write.log`, `server-read.log`, and their console captures. Manifest hashes include the installed classes or their jar entries and vanilla Lua used for verification. The earlier standalone feasibility probe remains in `diagnostics/vault-prototype/` as historical evidence.

During development, the extended native probe rejected the bare-edge implementation because the C++ pathfinder required wall metadata. The metadata repair then passed both classifiers and the public native entry. The initial feasibility probe did not test those conditions; it is not sufficient evidence by itself.

The headless server has unrelated stock/PZ Optimizer startup warnings already present in earlier runs; no player connected. Rendered animation, real-map landing/collision, client load order, zombie attacks during a player vault and owner acceptance remain open. Multiplayer construction/combat/service/vaulting remain gated. No final art or new recipes were added.

## Owner test

1. Restart PZ into **0.2.4** on a disposable SP save. Enable OMHTT diagnostics and Foundation Test Controls; confirm the version in the test menu. Use normal speed, default Damage 10 / HP 100, God Mode off and No Clip off. Have five loose barriers and free inventory capacity; Build Cheat can cover construction requirements.
2. In Building, create barriers in all four orientations, including Deploy Spike Barrier. Check the two-tile preview, categories and wrapped statistics. Pick up/redeploy an older built barrier to convert it. Walking across each new edge must be blocked.
3. Stand directly behind either half and choose **Spike Barrier > Vault**: cross with the fence animation, no scratch and no stuck movement. Repeat from the front several times: only completed front crossings have the 20 percent scratch roll; an injury is not guaranteed every fifth attempt.
4. Block the landing with an object or occupant: Vault must be unavailable. Let zombies thump from the front/rear and during a player vault: default retaliation is 10 at front/side, zero at rear; zombies must remain blocked. Destroy one barrier: both parts/collision should disappear without errors.
5. Use the developer condition option to damage another barrier. Start Repair, cancel by walking, then finish it: ten active seconds to full HP, no materials. Cancel/finish Pickup: ten seconds, exactly one item and both halves removed. Redeploy at full HP.
6. Pack/unpack five loose barriers: five back, no XP from packing or deployment. Save/reload; check edge direction, collision and shared durability. Separately test Sandbox Damage 5 / HP 200 and repair to 200.
7. Exit to menu and reply **Test Complete** so console.txt can be reviewed for version, services, damage, crossing results and errors. A screenshot helps if the unchanged placeholder's position makes the blocking edge difficult to read.
