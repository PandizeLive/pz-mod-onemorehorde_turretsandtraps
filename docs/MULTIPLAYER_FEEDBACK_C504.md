## Confirmed mechanisms and limits

1. **Server square membership is not reliable physical contact.** Native `NetworkZombiePacker.applyZombie` sets x/y/z from `ZombiePacket.realX/realY/realZ`, but sets current square from the packet's predicted x/y/z, then moves square-list membership to that current square. `getSquare()` and a tile's moving-object list can consequently disagree with the actor's actual coordinates. BedRuntime selects its exact bed through `getSquare`; Poke examines only its own moving-object list. DefenseContacts and turret search also discover actors through those lists. Barb contact verifies real coordinates but first finds its bucket through `getSquare`, so sufficiently displaced predicted membership can omit a legitimate contact. Reproduction: identical real landing over a bed is missed with an adjacent predicted square and hits when square/coordinates agree. Poke similarly misses a real occupant in the adjacent predicted bucket. The earlier fixtures kept these aligned; their passing results did not cover this native packet behavior.
2. **Poke retains a delayed crossing hole.** On detection it schedules a strike 150ms later, then checks only actors still in that square. A crossing between activation and strike receives no damage. This is separate from the removed initial one-second delay. Its current 1.5-second cycle also intentionally prevents continuous firing. Do not silently remove repeat cooldowns or damage actors long after leaving; review immediate first-contact behavior in the corrective scope.
3. **Range arithmetic works in the reviewed paths, but acquisition scales poorly.** Shared `TurretStats` includes Range modules and both display/automation build profiles from those stats. Improvised Detection and the engagement slider can still restrict automatic range. `TurretAutomation.advance` consumes up to64 square/actor units per visit; selection waits for completion of the entire area. A fully loaded fixture with one target takes six visits at9tiles and38 at24tiles. At the observed100ms server cadence, acquisition alone can take roughly half a second versus several seconds, before intended wake/alert timing. This is a reproduced latency mechanism, not proof that every reported Range miss has this cause. Deadline contention and predicted bucket membership may add delay.
4. **Visual endpoint and damage eligibility disagree.** `DefenseEffects.emit` removes the local target reference without sending a replacement identity. Multiplayer `PrototypeEffects` therefore renders the old numeric endpoint; SP can follow the live actor. `PrototypeCombat.arrive` still accepts the intended target up to2tiles from the launch endpoint. A production replay accepts a1.5tile displacement while the MP packet retains the old point. Fix the shared shot contract so presentation follows the same validated intended target/trajectory, including misses; do not fabricate hits for visual smoothness.
5. **Rejected hits do not invalidate automation's target.** `DefenseCombatClient` can reject missing/dead/recycled/non-owned actors, position disagreement over8tiles, invalid fields, capacity or expiry. It returns generic Reject. Server `finish` supplies a generic failure to the damage callback, while `TurretHit.resolve` only invokes shot effects on positive loss. No rejection result reaches retained target selection. A server-stale target can therefore continue consuming shots until another validity check changes. This is a codepath weakness consistent with the report; which guard produced the396 replies remains unknown. Filter only changes priority/retention policy; removing it is not a demonstrated fix.
6. **Authority is split around native zombie ownership.** The server selects targets, validates rules and calculates damage/resources. Native B42 delegates zombie simulation to an owning client. For client-owned zombies, T&T sends Prepare, receives Ready, sends Commit and receives Applied; the server settles health/death/XP and broadcasts presentation. Ownerless damage is applied on the server. Extra round trips and stale server observations affect responsiveness; another visual smoothing layer cannot fix them. Do not replace this with unrestricted client damage or let arbitrary observers authorize contact.
