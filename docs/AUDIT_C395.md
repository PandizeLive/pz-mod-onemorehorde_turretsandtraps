## Controller expansion - decision 1

Owner specifies base radius 10 tiles, base stockpile 100 weight, +10/+100 per expansion step, slot beside the battery on the right, and Modules Sandbox controls. Existing kits are Improvised, Small, Medium and Large; no new rarity/loot weight is required if those exact items are reused.

- **1A (recommended): one expansion slot, existing kit grades define steps.** None 10/100; Improvised 20/200; Small 30/300; Medium 40/400; Large 50/500 (radius/weight). A better kit replaces the installed kit; installing Large directly does not require consuming prior grades. Same recognizable progression as turret expansion, no unlimited stacking.
- **1B: stack existing kits, each adds 10/100 regardless of grade**, proposed cap four kits, maximum 50/500. Simpler counting but removes the grade distinction for Controllers and needs stacked-slot presentation.

Proposed safeguards under either choice: preserve all stored items when capacity shrinks, allow withdrawal but reject additional deposits until under capacity; block kit removal if it would overfill stockpile. Keep out-of-range assignments recorded but inactive and visibly identified rather than silently deleting links. Apply radius/capacity consistently in UI, stockpile transfers and server authority. Keep installed kit state across pickup/place/save/restart. Shared kits must work with Traps alone without duplicating registrations/loot when both entries load. Preserve current item rarity, LootLab weights and overrides. Base radius/capacity settings belong with Controller settings; kit bonuses/limit belong under Modules > Expansion Kits. Resolve old ControllerRange overrides explicitly instead of silently reinterpreting them as a kit bonus.

## Sandbox audit and LootLab - decision 2

The source has 211 options in ten pages: General 3, Traps 21, Turrets 67, Automation 3, Modules 48, Loot 43, Debug 7, Poke 5, Triggers 7 and Tether 7. Poke and Tether are indeed separate sidebar pages, contrary to the owner's intended per-trap sections inside Traps. Existing `SandboxUI` grouping did not solve that. Consolidate all traps into Traps with internal named groups; retain head groups inside Turrets, and separate Triggers/Modules/Loot for their distinct roles. Preserve stable option IDs and saved values. Review duplicate package presentation, meaningful labels/units/defaults, redundant controls, missing groups and runtime consumers before declaring an option obsolete. Internal historical Potato-prefixed keys can retain compatibility while display labels describe their actual scope. Do not delete settings just because their names are legacy.

`ModuleLootRate` really defaults to 1.011111111111111 and `sync_defaults.apply_defaults` exports that raw value as LootLab global. The live log confirms it is used. Cosmetic formatting and retuning are different changes.

- **2A (recommended): display sensible precision, preserve full stored/calculated values.** This default displays 1.01, not 1.00. Normal editing can use .01 steps for this multiplier, but merely viewing/saving untouched settings must not quantize existing weights. Smaller probability/consumption controls need suitable precision, not blanket two-decimal rounding. Capitalize Module Loot Multiplier and audit other labels. No LootLab rebalance is required for formatting alone.
- **2B: also reset the global default to exactly 1.00.** This reduces global loot about 1.10% relative to 1.011111111111111, so align exported defaults/LootLab baseline deliberately while preserving item/tier overrides and existing saved scenarios. No hosted deployment is implied by this discussion.
