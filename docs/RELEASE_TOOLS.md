# OMH local development and release process

Current GitHub policy is [GITHUB_WORKFLOW.md](GITHUB_WORKFLOW.md), approved under C96 on 2026-10-07: private full repository, default `dev`, Cloud planning PRs into `dev`, and `main`/official Releases reserved for confirmed publication. Existing local test tags and package versions are unchanged.

Reviewed the current Horde Night [working agreement](../../pz-mod-onemorehorde_protectthecure/AGENTS.md) and [release-tool documentation](../../pz-mod-onemorehorde_protectthecure/docs/RELEASE_TOOLS.md) on 2026-09-26. Its repository-specific remote, Workshop item, reviewer and paired-package assumptions are not copied into this standalone project.

## Naming

- Product name: **OMH: Turrets & Traps**. Independent entries are **OMH: Traps** (`OneMoreHorde_Traps`) and **OMH: Turrets** (`OneMoreHorde_Turrets`). C88 explicitly authorizes new IDs and fresh worlds; preserve existing item/state keys, but do not promise old combined-save migration.
- New versions use `major.minor.patch`, with a fourth numeric field for a small corrective build. Checkpoint labels belong in documentation, not `modversion`. The footprint change is `0.1.6`; a subsequent small correction would be `0.1.6.1`.
- Use `docs/PHASE_2_CHECKPOINT_1.md` for the current construction checkpoint, `docs/PR_v<version>.md` for release notes, and annotated local tag `test/v<version>` for exact source rollback. Historical checkpoint files, suffixed versions and their evidence retain their original names.
- Root [OMH.cmd](../OMH.cmd) and the owner-requested [OMH_TurretsAndTraps.cmd](../OMH_TurretsAndTraps.cmd) open the same menu, with stable helpers in `tools/` and version read from packaged `mod.info`. No per-version launchers. The two older launchers are retained in [an archive](../artifacts/legacy-launchers.zip).

## Process

1. Review the completed owner test and its exact loaded version; record evidence and unresolved limits before editing. Scope the patch to the approved behavior.
2. Implement and run the smallest meaningful checks; update checkpoint, decisions, current release notes and the cumulative `WORKSHOP_CHANGELOG.txt`. An install or version bump never resets pending Workshop notes.
3. Preserve complete source on a local non-main working branch, commit it and create an annotated `test/v<version>` tag before deployment. The installer requires unchanged tagged Source and Contents and a matching validated SHA-256 manifest. Later tooling/documentation-only commits may follow the gameplay tag while Source and Contents remain byte-identical, matching Horde Night's existing practice. Local Codex-authored commits use an explicitly local agent identity, not an invented owner identity.
4. Install locally with a full managed-folder backup and verify copied hashes. Install-Packages.ps1 stages and hashes both entries before replacing managed folders. It preserves unrelated files, retains full backups, retires the old managed combined entry into the backup and rolls back both packages on failure. Fixtures inject a second-package move failure to verify rollback. Modified managed files or unmanaged destination folders cause refusal. Never call readiness checks a successful install or test.
5. Establish the intended loaded version before evaluating gameplay. The native server smoke can prove startup separately; the owner's first SP test step verifies the actual client developer-menu version. An installed manifest alone does not prove the running client loaded it. Prefer SP while it can answer the question; combat MP acceptance remains deferred.
6. Review the test log and update the tested version's acceptance record. C108 requires committing and mirroring every completed update and test finding through option 2 / OMH.cmd -Action Mirror under standing authorization, without waiting for another patch or push request. The private GitHub remote is configured under C96. C492 prepares native Workshop staging and an update-only unlisted publisher. The owner performs the first in-game upload; the updater then reads its ID. Preserve owner-authored Workshop text/cover. See [C492 workflow and evidence](WORKSHOP_UPLOAD_C492.md).

The stable menu retains **1 Install locally**, **2 Mirror development to GitHub**, **3 Update unlisted Steam Workshop item**, **4 Check local install readiness**, **5 Check Workshop update readiness**, **6 Project-specific tools**, **0 Exit**. Actions 3 and 5 require the first in-game upload's ID. Option 2 supports committed development/planning checkpoints without requiring a new version; short-lived branches get draft PRs into dev. Option 6 offers native Workshop staging, read-only staging checks and existing diagnostic capture. It does not upload logs.

CLI checks: `OMH.cmd -Action Info`, `OMH.cmd -Action Mirror -ValidateOnly`, `OMH.cmd -Action Install -ValidateOnly`, and `OMH.cmd -Action Capture`. Python native validation remains `tools/validate_foundation.py`; release-tool fixtures are in `tools/test_release_tools.py`, and development-mirror preflight fixtures are in `tools/test_github_workflow.py`. Installation does not modify saves, enabled-mod selections or sibling projects.

For 0.2.9, the game is 42.21.0 while installed PZOptimizer loose overrides still target 42.20.4. Set `OMHTT_STOCK_CLASSES=1` for isolated validation and smoke probes to put the stock game JAR first; the manifest records that class order and hashes the classes actually used. This does not fix or modify the normal game installation. Run `tools/smoke_server.py` first with `OMHTT_PROBE_MODE=write`, then `read` for a fresh-process restore. The owner later demonstrated ordinary client startup on 42.21; this isolated-probe mismatch is not a current confirmed player blocker.


## C498 - local authoring copies during test installs

Before handing off a local test install, inspect the existing managed native Workshop stage for the same mod IDs as well as the ordinary mods folder. Zomboid42.21 searches staged Workshop content before Steam downloads and local mods by default. Publishing the frozen Contents snapshot does not refresh the authoring stage. If an existing managed stage is stale, use `OMH.cmd -Action Stage` and verify its packaged hashes before requesting a restart/retest. Preserve owner metadata and the helper's backup; never overwrite an unmanaged or edited stage. Do not create a new authoring copy merely to test a subscribed package. C498 exposed this delivery omission even though the uploaded Steam package and server were current.
